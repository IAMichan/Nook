# Connecting Coding Agents to Nook

Nook displays what your AI coding agents are doing right inside the notch. Any agent that can invoke a shell command or write to a Unix domain socket can report to Nook and get its own dedicated session row.

Everything stays on your Mac: events travel over a local Unix socket (`0600`) that only your user account can open. If Nook is not running, the hook script exits cleanly as a no-op and the agent continues without interruption.

## Built-In Integrations

In **Settings › Agents**, you can connect these agents with one click. Nook previews the exact file changes first, creates a timestamped backup next to the configuration file, and writes only after your confirmation. Any file that cannot be read or contains invalid JSON is left untouched, as is any plugin file not created by Nook.

| Agent | Configuration File | Mechanism | What You See |
|---|---|---|---|
| Claude Code | `~/.claude/settings.json` | hooks, `--agent claude-code` | progress, approvals, questions |
| Claude (Desktop app) | same hooks | detected via `CLAUDE_CODE_ENTRYPOINT=claude-desktop` | progress, approvals, questions |
| Codex | `~/.codex/hooks.json` | hooks, `--agent codex` | progress, approvals |
| Gemini CLI | `~/.gemini/settings.json` | hooks, `--agent gemini` | progress |
| Antigravity (`agy`) | `~/.gemini/config/hooks.json` | dedicated `nook` group, `--agent antigravity`, space-free path via `~/.nook/nook-hook`, no `PreToolUse` | progress |
| Cursor | `~/.cursor/hooks.json` | hooks, `--agent cursor` | progress |
| Copilot CLI | `~/.copilot/hooks/nook.json` | dedicated file, `--agent copilot`, `preToolUse` waits (`--wait`) | progress, approvals (where Copilot would ask) |
| Muse Code | `~/.config/muse/settings.json` | hooks, `--agent muse`, `PermissionRequest` waits | progress, approvals |
| OpenCode | `~/.config/opencode/plugins/nook.js` | plugin | progress, approvals (`permission.asked`) |
| Amp | `~/.config/amp/plugins/nook.ts` | plugin | progress |
| Hermes | `~/.hermes/plugins/nook/` | plugin, then `hermes plugins enable nook`; for approvals `security.approval.transport: nook` (and `transport_fallback: builtin`) in `~/.hermes/config.yaml` | progress, approvals |

Restart the agent after connecting. Approvals from the notch work for Claude Code, Codex, Copilot CLI, Muse Code, OpenCode and Hermes, and for the Claude app's own computer-use prompt (Nook presses its button). Gemini CLI, Antigravity, Cursor and Amp give a hook no way to allow a call, so for those Nook never blocks and the agent asks you in its own UI; in sessions Nook runs itself every agent asks in Nook. Without an answer in Nook, every agent falls back to its own prompt. An agent connected with an older Nook shows **Update** in Settings › Agents.

## Supervising & Controlling Agents

If you quit and reopen Nook, agents that kept running in your terminal reappear immediately: Nook persists known hook sessions (`agent-sessions.json`) and restores them, pruning any session whose process has exited on the first scan.

All agent sessions converge in a single registry (`AgentSessionRegistry`): hooks, process scanning, transcripts, and sessions launched by Nook itself are deduplicated so each conversation appears once, while two processes in the same folder remain two separate rows. Internal helper processes spawned by Nook (`NOOK_RUN_ID` or `NOOK_INTERNAL`) are excluded and never terminated.

- **In the Notch** (**Agents** tab, compact view): see what is running and what is waiting for you, approve or deny tool calls, answer multiple-choice questions, and send quick follow-ups. Clicking **New Session** opens the workspace window; accounts are managed in Settings.
- **In the Main Window** (`⌥⌘W` › **Agents**): full conversation timeline, inline approvals, stop (`⌘.`), resume, retry, and per-turn mode, permission, and model controls. The right inspector displays branch, worktree, changed files with diffs, **Commit**, **Push**, and **Pull Request** actions.

- **Pull Requests** (**Agents** › **Pull requests**): every open GitHub pull request you wrote or are asked to review, per connected account, plus the open pull requests of the organizations (`acme`) and repositories (`acme/web`) you add under **Settings › Pull requests** (shown as **Watched**, searched with every connected account). A search by title, repository, `#number`, `@author` or branch (`⌘F`) that also takes qualifiers (`label:bug`, `label:bug,ui`, `-label:wip`, a scoped label such as `area:ui`, `author:ada`, `draft:false`, `review:approved|changes-requested|required|none`, `checks:failing|pending|passing`, `repo:owner/name`), a **Sort** button (sort order and grouping) and a **Filters** button (state, involvement, author with counts and a search, labels in their colors with counts, drafts, review decision, checks, repository). The filters are kept across launches. Rows show GitHub's state mark with a conflict warning on it, then the number and title with the checks, review decision and lines changed; under it the author's picture, the repository, up to three colored labels, the place in a stack and when it last changed; group headings carry a count. Clicking one opens it inside Nook, beside the list when the page is wide enough (the open row highlighted) and in its place otherwise: a fixed top with the repository and the number in its state's color (a click opens it on GitHub), the main action (**Merge** with its method, **Ready for review** for a draft, or the state), the ⋯ menu, then the title (up to two lines), author, the branches (a fork's branch with its owner, `ada:feature`) and the size; once you scroll past the title it folds to one line. Under it four tabs: **Summary** (a **Status** line with the verdict and the one thing that matters most, which opens every merge condition with a shortcut to act on each (this is where a branch that is behind is updated, besides the ⋯ menu), reviewers ringed by their verdict (a team asked for a review shows a team mark), labels, and only when set the assignees, the issues it closes (open or closed, a click opens one), the milestone, a locked conversation with GitHub's reason, and auto-merge with its method and who turned it on, then the description, the checks and the comments in sections that fold; a thread on a line keeps its replies under its first comment with the file, the line and **Outdated** when a push moved the code, comments show their emoji reactions, a resolved thread or dismissed review folds to one line, a **Filter** menu shows bot comments and resolved or dismissed ones, and the ten most recent conversations show first with **Show older conversations** for the rest), **Guide**, **Timeline** (reviews, (line) comments, commits (a **…** unfolds a commit's whole message), labels, review requests, force-pushes, mentions, the merge) and **Code** (each changed file with its diff). The bar beside the tabs shows the comment, commit and approval counts with the order on Timeline, and the files viewed on Code. Opened pull requests stay as tabs above the page once a second one is open (at most eight; the right-click menu closes one, the others, the ones to the right, or all). Holding **Shift** shows quick actions at the end of each row (close and merge, close and ready for review for a draft, reopen); the first click asks to confirm, the second sends it, and each is logged (`github_close_pr`, `github_merge_pr`, `github_ready_pr`, `github_reopen_pr`). A quick merge checks the pull request again first (open, no conflict, write access, no failing checks) and uses the merge method last picked on a page. Pull requests whose base branch is another open pull request's head form a **stack**: rows show their place (`2/3`), and the page's stack menu opens another one of it or merges the stack from the bottom up to the one you read, pointing each next one at the base branch first (`github_change_base`). With more than one GitHub account, **Filters › Account** lists one of them. Ready for review is also in the page's ⋯ menu for a draft, and **Convert to draft** turns an open pull request back into a draft (`github_draft_pr`). **Merge** (merge commit, squash, or rebase, as the repository allows, picked from the arrow beside it) asks for a second click (**Confirm merge?**), shows a quiet warning mark beside it when GitHub may still hold it back (a click explains why), pins the head commit you looked at (GitHub refuses if someone pushed since), uses the account the pull request is listed under, and logs the result to the action log (`github_merge_pr`). Rows show the review decision (approved, changes requested, review required), a conflict mark and up to three labels; the list sorts by merge readiness, by what is blocked on you, or by size. On the page, the round button at the bottom right opens a composer for a comment or a review (comment, approve, request changes), the ⋯ menu copies the link, number or `gh pr checkout` command, requests reviewers, edits the title and description, updates an out-of-date branch, and closes or reopens it. Reviewers can also be asked from the **+** after the reviewers on **Summary**, or from **Ask for a review** on the *No reviews yet* line: the field offers the people who can review the repository (not the author, not a bot, not someone already asked) as chips to pick, and still takes logins typed by hand. Every write asks for a second click and is logged (`github_review_pr`, `github_comment_pr`, `github_close_pr`, `github_reopen_pr`, `github_edit_pr`, `github_request_reviewers`, `github_update_branch`). Files read in order (source with its tests, then docs, then generated files); a file you marked viewed and that was pushed to since says **Changed**. The timeline can be read newest first. A github.com pull request link in a session's conversation opens in a **Pull request** tab in that session's side panel (in Nook's own chat, on this page); its ↗ button opens it on GitHub. That tab opens on the session's own pull requests: the ones of its branches and the ones you linked (by link, `owner/repo#12`, `#12` or a number), a chain indented under what it is built on, each with a ⋯ menu to copy, open, watch or take it off the list, and a line at the bottom with how many are open and linked and when they were last read; your other pull requests follow below them. On the page, the checks sit beside the tabs on **Summary** (a click lists them, what needs you first), the headings of **Summary** stay in sight while their section scrolls, a warning on the base branch says it is out of date and updates it, the lines changed split into code, tests, mocks, generated files and docs on hover, a pencil edits the title and description, and beside a session a comment can go to its composer on its own, **Fix findings** hands over everything still open, and **Resolve in this session** takes the place of the conflict badge. **Code** shows every file in one scroll, or one commit from its menu (a commit on **Timeline** opens it there), with a tree, split view, wrapping, hiding tests and a viewed mark per file; comments written on lines wait and go out together with the review (**Finish review**), and conversations stand under their line. Threads can be answered and resolved, your own comments edited, and emoji added or taken off a comment (these two go at once, logged as `github_react` and `github_resolve_thread`; everything else keeps its second click). The ⋯ menu also updates a branch with a rebase, turns auto-merge on or off (the main action while checks run or reviews block), edits labels, allows maintainers' edits, reverts a merged pull request, deletes a finished branch and writes the review guide. A session can watch any number of pull requests. A row can be dragged into a composer. Pull requests open the same page on GitLab, Gitea, Forgejo, Bitbucket, Azure DevOps and GitCafe, showing what each forge offers, with tokens under **Settings › Pull requests**. The ⋯ menu checks one out in a worktree, in the folder itself (refused with local changes) or on an SSH machine. Shift on a second line's **+** comments on a range; the Guide unfolds a stop's files to comment there too. Emoji go on the description. GitHub's own stacks show in the stack menu and merge in one go. With Shift held, dragging **Close** over other rows closes them after one confirmation. The session panel's rows show the checks, the watch and one action (**Resolve**, **Ready**, **Fix**, **Merge**).

Key capabilities:
- **Unified Approvals** (`ApprovalCenter`, `ApprovalView`): shows the complete command or file diff, risk level, and **Allow**, **Always**, **Deny**, or **In Terminal**. Approving in the window or terminal immediately clears the notch card.
- **Running Sessions:** Continue a busy external session safely as a fork (`--fork-session`) so two writers never collide, or choose **Take Over** (`⋯`) to stop the external process and continue the session directly inside Nook.
- **Sessions Managed by Nook ("In Nook"):** Supports Claude Code, Codex, Gemini CLI, OpenCode, Cursor, Grok, and Antigravity with persistent per-session connections: Codex via `codex app-server`, Claude Code via a persistent streaming process, and others via ACP. Includes git checkpoints in isolated worktrees, auto-generated session titles, one-click Commit / Push / PR (always in English), and automatic resume when rate limits reset.
- **Back to Before a Message:** right-click one of your messages in a worktree session › **Restore files to before this message** puts the files back to the checkpoint before it. Claude Code and Codex (over app-server) also forget that message and everything after it: Codex drops those turns from its thread (`thread/rollback`, or `thread/revert` on newer Codex), Claude Code resumes a copy of its conversation at the last message that stays (`--resume-session-at` with `--fork-session`). The rollback goes out with your next message; the undone part of the timeline shows dimmed and the checkpoints after that point are removed. Other agents keep their conversation (`ProviderCapabilities.canRollbackConversation`, `ConversationRollback`).
- **Going On After a Restart:** with **Settings › Agents › Sessions › Behavior › Continue a session cut off by a restart of Nook** on (off by default), a session that a restart or update of Nook cut off in the middle of a turn gets "Continue where you left off." a moment after launch. A session whose turn had ended while it waited on a subagent in the background that the restart stopped gets a note naming that work first, so it starts again what it still needs. Never a session you archived, settled or snoozed, one stopped by a usage limit, or one that was waiting for your answer or approval; at most three times in a row within five minutes, so a session that keeps crashing Nook does not loop (`RestartContinuation`).
- **Steering Every Agent:** Claude Code and Codex take a message into the running turn. An agent without native steering (the ACP agents, Gemini CLI) is steered by an interrupt instead: when you steer (`⌘↩`, or every message during a turn with **Settings › Agents › Sessions › Behavior › A message during a turn steers the agent** on) Nook stops the turn and sends your message as the next prompt; never while a question or approval waits for you (`SteerRoute`). What each agent can do is in `ProviderCapabilities` (steering, rollback, fork from a turn, whether pending requests survive a restart, how reliably a turn's end is signalled).
- **Deny with a Reason:** an approval card has **Deny with reason**: type why (or what to do instead) and Return denies it and tells the agent. Claude Code gets the text in its answer to the request (and a terminal agent in its hook's reason); Codex and the ACP agents, whose decline has no text, get it as a message right after: a steer for Codex, the next prompt after an interrupt for the others (`ProviderCapabilities.denyReason`). On the iPhone, what you type under an approval does the same.
- **`/clear`:** starts a new conversation in the same session, folder and branch. The timeline stays, with a **New conversation** divider; the agent forgets everything above it, also when you switch agents later (`WorkspaceManager.clearConversation`). `/clear` sets your next message to start it; a strip above the composer says so and **Keep this conversation** takes it back. Sent while the agent works, that message waits in line (marked with an eraser) and starts the new conversation after the turn. When a turn fails because the agent lost its conversation or it no longer fits the context, Nook starts a new one by itself from the timeline and sends the message again, once. ⌥⌘Return sends and opens a new session's composer.
- **How Much of the Work Shows:** **Settings › Agents › Sessions › Behavior › Agent's work in the timeline** (and per session in its menu): everything, without finished steps, without steps, or Zen (your messages and each turn's last answer). Requests that wait on you and errors always stay; the find bar searches everything (`TimelineDetail`).
- **Speed Tier:** beside the effort, a pill picks Standard or a faster tier of the same model for the next turns: Codex's own tiers per model (`serviceTier`), Claude Code's fast mode. It is not kept for new sessions, because faster costs more (`SpeedTiers`).
- **`@` a Model:** type `@` and part of a model or agent name (`@opus`, `@gpt-5`, `@opus:opencode`) to name that model for a subagent or a delegated task; the session keeps its own model (`ModelMention`).
- **Cloud Sessions:** Sessions in Anthropic's cloud (started in the Claude Mac/iOS app or on `claude.ai/code`) are not read by Nook.
- **Claude Subscription Login:** Nook never uses Claude Code's subscription login (OAuth token) itself; Anthropic allows it only in Claude Code and claude.ai. Everything Claude-related goes through the official `claude` CLI. The 5-hour and weekly limits come from Claude Code's status line and the `rate_limit_event` messages of sessions in Nook, and while those are quiet Nook asks the unmodified `claude` binary for them with the `get_usage` control request (the numbers behind `/usage`): without a prompt and only for signed-in accounts: in the background at most every ten minutes, and sooner when it matters — when you open the usage overview (every two minutes while it stays open) and after a Claude turn in Nook, at most once a minute per account; the refresh button in those views reads them at once (at most every ten seconds) (all slower when the energy plan takes it easy). The CLI uses its own login; Nook never reads, stores or forwards it. They are kept between launches.
- **Open What the Agent Points At:** a file link in an agent's answer (`src/app.swift:12:3`, `./README.md`, `#L20` anchors, `file://` links) opens in your editor at that line, read from the session's folder; in Nook's terminal, ⌘-click opens a local address in Nook's browser, any other web address in your browser and a path in your editor. Each editor gets the position its own way (`--goto` for VS Code, Cursor, Windsurf and VSCodium, `path:line:col` for Zed and Sublime Text, `xed --line` for Xcode, `--line`/`--column` for JetBrains), and a file is never opened in its default app. Changed files have a right-click menu: open in editor, show in Finder, copy the path or the path in the repository.
- **What a Session Costs:** a working session's header shows the CPU and memory of its agent and every process it started ("34 % · 512 MB"), read every three seconds while the session is on screen (`ResourceUsage`).
- **Worktrees That Clean Up After Themselves:** **Settings › Code › Worktrees** has the same cleanup rules, and **all of them are off by default**: a worktree stays until you remove it, so after a merge you can go on talking to the agent that did the work. You can switch on removal once the session's pull request is merged, 3, 7 or 30 days after the session settled (marked finished or archived) and went quiet, 3, 7 or 30 days after the session went quiet whether or not it settled, when the worktree has no commits beyond its base branch, or when the last session in it is deleted (then **Delete** does it, and the separate **Delete with worktree** button goes). **Keep a worktree with** sets what counts as local changes: uncommitted changes (the default: edited and untracked files keep it, ignored files such as builds go with it), any local files (ignored files too, except `node_modules`), or edited tracked files only. Each project can switch cleanup off (**Automatic worktree cleanup** in its defaults). The rules run at launch, every hour, when you change one, and with **Clean up now**; the latest results list each worktree a rule applied to, removed, kept (and why) or failed, the space freed, and the folders in Nook's worktree folder that no session uses (untouched for an hour), with their size. Nook only reports those folders and never removes them. A worktree is always kept while it is in use (a turn, the agent's process, a terminal open in it), when another session shares it, when it is the main checkout, a symbolic link, on another machine, when another branch is checked out in it, or when it has local changes. After a merge it is also kept while it has commits that are on no remote. The branch and the conversation stay. The session's next message makes the worktree again at the same path: on its own branch while the work is not merged, and from `origin/<branch>` when the local branch is gone. Once merged it gets a new branch from the base, so it gets its own pull request. A merged pull request settles a session (when that rule is on) only if it merged after you last wrote to the session. Antigravity's private TMPDIR, which macOS never empties, is cleared of anything older than two days when a session starts (`DiskUsage`). Every six hours Nook also removes build leftovers a worktree removal cannot reach: Xcode build folders and core-tests packages in temporary folders, Claude Code scratchpads, and the `.scratch/` of any worktree Nook knows (its own, its sessions', and `.claude/worktrees` in the repositories it works in) that went untouched for two days, and Xcode DerivedData of worktrees that no longer exist (`BuildLeftovers`, logged as `build_cleanup`). Every removal goes to the action log (`worktree_cleanup`). Checkpoints, restores and removals of the same folder run one at a time (`WorktreeCleanup`, `FolderLease`).
- **Sessions Working at Once:** **Settings › Agents › Sessions › Behavior › Sessions working at once** (no limit by default) caps how many sessions work at the same time. A turn past the limit shows your message, says it waits, and starts first come first served as soon as another session's turn ends, however it ended; Stop cancels it. A delegated task that waits reads as `queued` for its parent (`SessionCapacity`, `WorkspaceManager.startWaitingTurns`). Turns that wait are not kept across a restart of Nook: such a session shows as stopped with your message, to send again.
- **Tidy Endings:** quitting Nook while sessions it runs are working asks first (not on logout, shutdown or an update restart; switch it off in **Settings › Agents › Sessions › Behavior**), and deleting a session offers **Delete with worktree** when no other session uses its worktree (Git refuses one with uncommitted changes, so nothing is lost).
- **Setting Up Coding Agents:** the first-run flow has a **Coding agents** step (also opened from the empty Agents list with **Set up coding agents**): Claude Code, Codex, Gemini CLI, OpenCode and Cursor each show whether they are installed and signed in, with **Install** or **Sign in** running the same connect flow as Settings › Agents in a visible Terminal window; ACP agents you added are listed, and more can be added in Settings › Agents. Below, the git folders your agents worked in during the last 30 days can be added as projects with one click (`AgentReadiness`).
- **Snooze, Delete and Drop on the List:** a session's snooze menu has, next to an hour, this evening and tomorrow,
  **Custom…** (a date and time, or a number of minutes, hours or days, up to a month) and, while a usage limit holds the
  session and Nook knows its reset time, **Until the usage limit resets** (a limit that was there when you snoozed does not
  wake it; a new one does). In the selection bar, **Delete** removes the picked sessions that are settled or archived
  (never one that works), after a confirmation, through the same path as deleting one session, so worktree cleanup
  rules apply. Files dragged onto a session's row open that session with the files attached to its composer: pictures
  as pictures, other files as references.
- **Sessions per Project:** the Agents list puts the sessions that work or wait in a dropdown per project, as in Claude's own sidebar: every session in the same folder sits under that folder's name, and a session in an agent's worktree (`.claude/worktrees/…`, Nook's, Codex's, Cursor's) under the repository it was made from (`WorktreeOrigin`). The projects keep a fixed place, in name order, so activity in one never moves the whole folder; inside a project the session with the newest activity comes first, with the sessions it started under it. A folded project still shows the session open on the right and a dot when something in it waits for you, and the folded projects are kept across launches. Pinned, snoozed and settled sessions keep their own shelves. **Settings › Agents › Sessions › Behavior › Group sessions by project** (on by default) switches back to the plain list (`InboxLayout.projectGroups`). This is the same list for every coding agent.
- **Where a Session Came From:** a session made with `/fork` (or **Fork**) keeps the session it came from (`WorkspaceRun.forkedFrom`, stored as its `lineage`). Its row in the Agents list carries a branch mark and sits under the original, and its header says **Forked from …** as a link that opens the original (a later model of a comparison says **Same prompt as …**). Sessions stored before this load unchanged.
- **Syntax Colors in Diffs:** every diff (a session's changes, a pull request's files) colors Swift, TypeScript/JavaScript, Python, Rust, Go, JSON, YAML, shell, CSS, HTML and Markdown. The diff shows plain at once; the colors are worked out in a background task (`SyntaxTokenizer`, `DiffSyntax`) and kept per file and content, so going back to a diff shows them right away.
- **Defaults per Project:** **Settings › Agents › Sessions › New session › Applies to** switches between the defaults for all projects and one of your recent project folders. A folder can set its own agent, model, access level, worktree on or off and branch prefix; every other value is marked **Inherited** and follows the global one, and the reset button next to an own value goes back to it. A new session in that folder (or a subfolder or worktree of it) starts with the result, and choices you make in the composer for a value the project sets stay out of the global defaults (`ProjectSettings`, built on `SettingsResolver`).
- **Stopping Stops Everything It Started:** every agent Nook runs gets a process group of its own (started with `posix_spawn` and `POSIX_SPAWN_SETPGROUP`), so **Stop** signals the agent together with the builds, shells and dev servers it started (SIGINT, then SIGTERM after the grace period, then SIGKILL). Live groups are written to `workspace/process-groups.json`; after a crash the next launch stops the groups an earlier Nook left behind, but only when the group leader is provably the same process (same pid, group and start time), never by name (`ProcessGroups.swift`).
- **Timelines That Survive a Crash:** a session's timeline is an append-only log in `~/Library/Application Support/Nook/workspace/runs.sqlite` (WAL, `0600`): each new event is written as it arrives, and a streamed answer or finished tool is written as a new version of that event, never by rewriting what is already there. Timelines are no longer cut off at 4,000 events (the panel still shows only the latest turns until you load earlier ones). The JSON timelines of earlier versions (`workspace/events/*.json`) are imported once and kept as a backup (`RunStore.swift`, `RunEventLog.swift`).
- **Replayable Agent Traffic:** `AgentProcess` talks to its agent through a `ProviderTransport`, so tests replay recorded transcripts (`apps/macos/Tests/Fixtures/ProviderReplay`, NDJSON: `emit_inbound`, `expect_outbound`, `expect_signal`, `exit`) through the real line handling and stream parsers (`ProviderReplayTests`). **Settings › Automation › Keep agent traffic** (off by default) writes the same format per session process to `workspace/provider-traffic` (`0600`, at most 4 MB per process): it holds your prompts and the agent's answers, never the environment, and a log can be copied into the fixtures to reproduce a bug (`ProviderTransport.swift`).
- **Commit Messages in Your Style:** **Settings › Code › Open in › Commit messages** picks how Commit and Pull Request write their text: Nook's own style, Conventional Commits, like the repository (its recent commit subjects as examples), or your own instructions (`CommitStyle`).
- **Pull Request Review:** tick files as viewed (a mark lapses when a push changes the file), and open the **Guide** tab for a review guide: Claude Code or Codex reads the whole diff and writes the stops in reading order, each file with a note, what to look at closely and what to skim, and the questions only a maintainer can answer. The guide stays on this Mac and says when it was written for an earlier commit.
- **Quote Part of an Answer:** select words in an agent's answer and right-click › **Quote in your message** to put just that passage above your next message. With several questions from an agent, **Back** returns to an earlier one with its answer still picked.
- **Usage of Every Agent:** **Agents › Usage** (tabs **Cost**, **Tokens** and **Limits**) and **Settings › Usage & costs** read the transcripts of Claude Code, Codex, Gemini CLI and Antigravity on this Mac (also sessions you ran in a terminal, for the last 90 days) and shows: cost at API list prices or tokens, over 24 hours, 7, 30 or 90 days; a large total with each agent's share; a stacked chart per agent (point at a column for its figures); totals for processed, cached and uncached input, output and cache savings; bars that split tokens and cost by type; and a breakdown per model (rank, share, a bar per model) or per day. A model opens with its cost per million tokens, cache hit rate and its own trend, and a model without a known price can get one (`UsageLedger`, `ModelRates`, `UsagePrices`). An agent with several accounts also shows them as one pool per limit window, a segment per account, with what the next reset gives back (`LimitPool`).
- **Full Transcript & Reasoning:** Reads agent transcripts to show collapsible reasoning steps (`thinking` / `thoughts`), commands, file edits, searches, and subagents inline. The conversation reads like a thread (`TranscriptPresentation`): your messages in a bubble on the right, answers as plain text on the left, steps in a row as one line ("Ran 3 commands and read 2 files"), each finished turn folded into "Worked for 1m 3s", and a running turn showing "Working for 12s" with the live step at its end and the thought that led to it right above. A message you sent while the agent worked splits the fold of its turn: the work after it folds into "Continued for 20s" under it. A turn you stopped stays open and ends in "You stopped after 12s". A context compaction ("Context compacted from 167k tokens"), an API error or a usage limit stays in sight when its turn folds. A command or another tool opens to its whole command line and what it gave back. A turn that changed files ends in a changed-files card ("3 changed files +12 −4", the files as a folder tree); a file in it, **Open diff** or `⌘D` opens the diff panel beside the conversation, where you pick the latest turn, any turn or all turns, and every file or one (`TurnDiff`, made from the agent's own edits). Sessions Nook runs get the same card and panel, with the lines and diffs read from git between the snapshots around each turn; when a turn pulls, merges or rebases, the files Git brought in are left out unless the turn edited, committed or fixed a conflict in them (`GitService.authoredPaths`), while restoring a snapshot still brings back everything. A message you sent while the agent worked, from Nook, the terminal or the Claude desktop app, shows as your prompt marked "Sent while working" (Claude Code writes it as a queued command); away from the end, a pill brings you back.

## Nook Workspace MCP for Your Agents

Agents can use Nook's integrated terminal, browser, and PR workflow via a local MCP server (`~/.nook/nook-mcp`): start a dev server in a visible Nook terminal (`terminal_run`, `terminal_read`), open, inspect and drive pages in Nook's browser (`browser_open`, `browser_read`, `browser_screenshot`, `browser_snapshot`, `browser_click`, `browser_type`, `browser_wait_for`), propose and watch a pull request (`pull_request_create`, `watch_pull_request`, `get_pull_request_status`), propose scheduled tasks (`schedule_task`, `list_scheduled_tasks`, `update_scheduled_task`, `run_scheduled_task_now`, always after your approval), and ask you for a named secret (`request_secret`). Sessions started by Nook receive this automatically; external agents can be linked in **Settings › Automation**. See [WORKSPACE-AGENTS.md](WORKSPACE-AGENTS.md).

## Connecting a Custom Agent

### 1. Via the Hook Script (Recommended)

The hook script is installed at:

```text
~/Library/Application Support/Nook/nook-hook.sh
```

Configure your agent to invoke it on each lifecycle event, passing the event JSON on `stdin`:

```json
{
  "hooks": {
    "UserPromptSubmit": [
      { "type": "command", "command": "\"$HOME/Library/Application Support/Nook/nook-hook.sh\" --agent my-tool" }
    ]
  }
}
```

- `--agent <name>`: Identifier under which the agent appears in Nook (lowercase letters, digits, `-`, and `_`, up to 32 characters).
- `<EventName>` (optional): Event name for agents that do not include `hook_event_name` in their JSON payload, e.g. `--agent my-tool Stop`.

### 2. Via the `nook_agent` JSON Field

If you cannot pass CLI arguments, include `nook_agent` directly in the JSON payload:

```json
{ "hook_event_name": "UserPromptSubmit", "session_id": "s1", "nook_agent": "my-tool", "prompt": "Write unit tests" }
```

### 3. Directly Over the Unix Socket

Send a single newline-terminated JSON line to:

```text
~/Library/Application Support/Nook/hub.sock
```

```json
{"agent":"my-tool","mode":"event","event":{"hook_event_name":"Stop","session_id":"s1","cwd":"/Users/you/project"}}
```

## Supported Hook Events

Nook normalizes event names from Claude Code and common aliases (`BeforeTool`, `preToolUse`, `beforeSubmitPrompt`, `PreInvocation`, `session_start`, etc.):

| Event | Nook Behavior |
|---|---|
| `SessionStart` | Marks the agent session as working |
| `UserPromptSubmit` | Starts a new turn; displays `prompt` as the current step |
| `PreToolUse` | Adds a running tool step (`tool_name`, `tool_input`) |
| `PostToolUse` / `PostToolUseFailure` | Completes the latest step as done or failed |
| `Notification` | Marks the agent as waiting for user attention; displays `message` in the notch |
| `Stop` | Marks the turn as finished; uses `last_assistant_message` as summary |
| `StopFailure` | Marks the turn as failed (`error`) |
| `SubagentStart` / `SubagentStop` | Tracks subagent lifecycle |
| `SessionEnd` | Removes the session from active lists |

## Quick Test

With Nook running:

```sh
echo '{"hook_event_name":"UserPromptSubmit","session_id":"t1","prompt":"hello","nook_agent":"demo"}' \
  | ~/Library/Application\ Support/Nook/nook-hook.sh
```

You will immediately see **Demo** in the notch with the prompt `"hello"`.

## Investigating Nook itself

**Investigate a problem with Nook** in the command palette fills a new session's composer with a draft (`NookTriage`): the
agent reads Nook's recent log lines, the source and the issues, and reports a likely cause. It stays away from Nook's
databases, chats, mail and keys, and asks before it changes or posts anything. Nothing runs until you send the draft.
