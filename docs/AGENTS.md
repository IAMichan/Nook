# Connecting Coding Agents to Nook

Nook displays what your AI coding agents are doing right inside the notch. Any agent that can invoke a shell command or write to a Unix domain socket can report to Nook and get its own dedicated session row.

Everything stays on your Mac: events travel over a local Unix socket (`0600`) that only your user account can open. If Nook is not running, the hook script exits cleanly as a no-op and the agent continues without interruption.

## Built-In Integrations

In **Settings › Agents**, you can connect these agents with one click. Nook previews the exact file changes first, creates a timestamped backup next to the configuration file, and writes only after your confirmation. Any file that cannot be read or contains invalid JSON is left untouched, as is any plugin file not created by Nook.

| Agent | Configuration File | Mechanism | What You See |
|---|---|---|---|
| Claude Code | `~/.claude/settings.json` | hooks, `--agent claude-code` | progress, approvals, questions |
| Claude (Desktop app) | same hooks | detected via `CLAUDE_CODE_ENTRYPOINT=claude-desktop` | progress, approvals, questions |
| Codex | `~/.codex/hooks.json` | hooks, `--agent codex` | progress, approvals |
| Gemini CLI | `~/.gemini/settings.json` | hooks, `--agent gemini` | progress |
| Antigravity (`agy`) | `~/.gemini/config/hooks.json` | dedicated `nook` group, `--agent antigravity`, space-free path via `~/.nook/nook-hook`, no `PreToolUse` | progress |
| Cursor | `~/.cursor/hooks.json` | hooks, `--agent cursor` | progress |
| Copilot CLI | `~/.copilot/hooks/nook.json` | dedicated file, `--agent copilot`, `preToolUse` waits (`--wait`) | progress, approvals (where Copilot would ask) |
| Muse Code | `~/.config/muse/settings.json` | hooks, `--agent muse`, `PermissionRequest` waits | progress, approvals |
| OpenCode | `~/.config/opencode/plugins/nook.js` | plugin | progress, approvals (`permission.asked`) |
| Amp | `~/.config/amp/plugins/nook.ts` | plugin | progress |
| Hermes | `~/.hermes/plugins/nook/` | plugin, then `hermes plugins enable nook`; for approvals `security.approval.transport: nook` (and `transport_fallback: builtin`) in `~/.hermes/config.yaml` | progress, approvals |

Restart the agent after connecting. Approvals from the notch work for Claude Code, Codex, Copilot CLI, Muse Code, OpenCode and Hermes, and for the Claude app's own computer-use prompt (Nook presses its button). Gemini CLI, Antigravity, Cursor and Amp give a hook no way to allow a call, so for those Nook never blocks and the agent asks you in its own UI; in sessions Nook runs itself every agent asks in Nook. Without an answer in Nook, every agent falls back to its own prompt. An agent connected with an older Nook shows **Update** in Settings › Agents.

## Supervising & Controlling Agents

If you quit and reopen Nook, agents that kept running in your terminal reappear immediately: Nook persists known hook sessions (`agent-sessions.json`) and restores them, pruning any session whose process has exited on the first scan.

All agent sessions converge in a single registry (`AgentSessionRegistry`): hooks, process scanning, transcripts, and sessions launched by Nook itself are deduplicated so each conversation appears once, while two processes in the same folder remain two separate rows. Internal helper processes spawned by Nook (`NOOK_RUN_ID` or `NOOK_INTERNAL`) are excluded and never terminated.

- **In the Notch** (**Agents** tab, compact view): see what is running and what is waiting for you, approve or deny tool calls, answer multiple-choice questions, and send quick follow-ups. Clicking **New Session** opens the workspace window; accounts are managed in Settings.
- **In the Main Window** (`⌥⌘W` › **Agents**): full conversation timeline, inline approvals, stop (`⌘.`), resume, retry, and per-turn mode, permission, and model controls. The right inspector displays branch, worktree, changed files with diffs, **Commit**, **Push**, and **Pull Request** actions.

- **Pull Requests** (**Agents** › **Pull requests**): every open GitHub pull request you wrote or are asked to review, per connected account, plus the open pull requests of the organizations (`acme`) and repositories (`acme/web`) you add under **Settings › Agents › Watched pull requests** (shown as **Watched**, searched with every connected account). A search by title, repository, `#number`, `@author` or branch (`⌘F`) that also takes qualifiers (`label:bug`, `label:bug,ui`, `-label:wip`, a scoped label such as `area:ui`, `author:ada`, `draft:false`, `review:approved|changes-requested|required|none`, `checks:failing|pending|passing`, `repo:owner/name`), a **Sort** button (sort order and grouping) and a **Filters** button (state, involvement, author with counts and a search, labels in their colors with counts, drafts, review decision, checks, repository). The filters are kept across launches. Rows show GitHub's state mark with a conflict warning on it, then the title (titles line up in one column) with the checks, review decision and lines changed; under it the repository and number, the author's picture, up to three colored labels, the place in a stack and when it last changed; group headings carry a count. Clicking one opens it inside Nook, beside the list when the page is wide enough (the open row highlighted) and in its place otherwise, laid out: a fixed top with the repository and the number in its state's color (a click opens it on GitHub), the main action (**Merge** with its method, **Ready for review** for a draft, or the state), the ⋯ menu, then the title (up to two lines), author, the branches (a fork's branch with its owner, `ada:feature`) and the size; once you scroll past the title it folds to one line. Under it four tabs: **Summary** (a **Status** line with the verdict and the one thing that matters most, which opens every merge condition with a shortcut to act on each (this is where a branch that is behind is updated, besides the ⋯ menu), reviewers ringed by their verdict (a team asked for a review shows a team mark), labels, and only when set the assignees, the issues it closes (open or closed, a click opens one), the milestone, a locked conversation with GitHub's reason, and auto-merge with its method and who turned it on, then the description, the checks and the comments in sections that fold; a thread on a line keeps its replies under its first comment with the file, the line and **Outdated** when a push moved the code, comments show their emoji reactions, a resolved thread or dismissed review folds to one line, a **Filter** menu shows bot comments and resolved or dismissed ones, and the ten most recent conversations show first with **Show older conversations** for the rest), **Guide**, **Timeline** (reviews, (line) comments, commits (a **…** unfolds a commit's whole message), labels, review requests, force-pushes, mentions, the merge) and **Code** (each changed file with its diff). The bar beside the tabs shows the comment, commit and approval counts with the order on Timeline, and the files viewed on Code. Opened pull requests stay as tabs above the page once a second one is open (at most eight; the right-click menu closes one, the others, the ones to the right, or all). Holding **Shift** shows quick actions at the end of each row (close and merge, close and ready for review for a draft, reopen); the first click asks to confirm, the second sends it, and each is logged (`github_close_pr`, `github_merge_pr`, `github_ready_pr`, `github_reopen_pr`). A quick merge checks the pull request again first (open, no conflict, write access, no failing checks) and uses the merge method last picked on a page. Pull requests whose base branch is another open pull request's head form a **stack**: rows show their place (`2/3`), and the page's stack menu opens another one of it or merges the stack from the bottom up to the one you read, pointing each next one at the base branch first (`github_change_base`). With more than one GitHub account, **Filters › Account** lists one of them. Ready for review is also in the page's ⋯ menu for a draft. **Merge** (merge commit, squash, or rebase, as the repository allows, picked from the arrow beside it) asks for a second click (**Confirm merge?**), shows a quiet warning mark beside it when GitHub may still hold it back (a click explains why), pins the head commit you looked at (GitHub refuses if someone pushed since), uses the account the pull request is listed under, and logs the result to the action log (`github_merge_pr`). Rows show the review decision (approved, changes requested, review required), a conflict mark and up to three labels; the list sorts by merge readiness, by what is blocked on you, or by size. On the page, the round button at the bottom right opens a composer for a comment or a review (comment, approve, request changes), the ⋯ menu copies the link, number or `gh pr checkout` command, requests reviewers, edits the title and description, updates an out-of-date branch, and closes or reopens it. Reviewers can also be asked from the **+** after the reviewers on **Summary**, or from **Ask for a review** on the *No reviews yet* line: the field offers the people who can review the repository (not the author, not a bot, not someone already asked) as chips to pick, and still takes logins typed by hand. Every write asks for a second click and is logged (`github_review_pr`, `github_comment_pr`, `github_close_pr`, `github_reopen_pr`, `github_edit_pr`, `github_request_reviewers`, `github_update_branch`). Files read in order (source with its tests, then docs, then generated files); a file you marked viewed and that was pushed to since says **Changed**. The timeline can be read newest first. A github.com pull request link in a session's conversation opens in a **Pull request** tab in that session's side panel (in Nook's own chat, on this page); its ↗ button opens it on GitHub.

Key capabilities:
- **Unified Approvals** (`ApprovalCenter`, `ApprovalView`): shows the complete command or file diff, risk level, and **Allow**, **Always**, **Deny**, or **In Terminal**. Approving in the window or terminal immediately clears the notch card.
- **Running Sessions:** Continue a busy external session safely as a fork (`--fork-session`) so two writers never collide, or choose **Take Over** (`⋯`) to stop the external process and continue the session directly inside Nook.
- **Sessions Managed by Nook ("In Nook"):** Supports Claude Code, Codex, Gemini CLI, OpenCode, Cursor, Grok, and Antigravity with persistent per-session connections: Codex via `codex app-server`, Claude Code via a persistent streaming process, and others via ACP. Includes git checkpoints in isolated worktrees, auto-generated session titles, one-click Commit / Push / PR (always in English), and automatic resume when rate limits reset.
- **Back to Before a Message:** right-click one of your messages in a worktree session › **Restore files to before this message** puts the files back to the checkpoint before it. Claude Code and Codex (over app-server) also forget that message and everything after it: Codex drops those turns from its thread (`thread/rollback`, or `thread/revert` on newer Codex), Claude Code resumes a copy of its conversation at the last message that stays (`--resume-session-at` with `--fork-session`). The rollback goes out with your next message; the undone part of the timeline shows dimmed and the checkpoints after that point are removed. Other agents keep their conversation (`ProviderCapabilities.canRollbackConversation`, `ConversationRollback`).
- **Going On After a Restart:** with **Settings › Workspace › Continue a session cut off by a restart of Nook** on (off by default), a session that a restart or update of Nook cut off in the middle of a turn gets "Continue where you left off." a moment after launch. Never a session you archived, settled or snoozed, one stopped by a usage limit, or one that was waiting for your answer or approval; at most three times in a row within five minutes, so a session that keeps crashing Nook does not loop (`RestartContinuation`).
- **Steering Every Agent:** Claude Code and Codex take a message into the running turn. An agent without native steering (the ACP agents, Gemini CLI) is steered by an interrupt instead: when you steer (`⌘↩`, or every message during a turn with **Settings › Workspace › A message during a turn steers the agent** on) Nook stops the turn and sends your message as the next prompt; never while a question or approval waits for you (`SteerRoute`). What each agent can do is in `ProviderCapabilities` (steering, rollback, fork from a turn, whether pending requests survive a restart, how reliably a turn's end is signalled).
- **Cloud Sessions:** Sessions in Anthropic's cloud (started in the Claude Mac/iOS app or on `claude.ai/code`) are not read by Nook.
- **Claude Subscription Login:** Nook never uses Claude Code's subscription login (OAuth token) itself; Anthropic allows it only in Claude Code and claude.ai. Everything Claude-related goes through the official `claude` CLI. The 5-hour and weekly limits come from Claude Code's status line and the `rate_limit_event` messages of sessions in Nook, and while those are quiet Nook asks the unmodified `claude` binary for them with the `get_usage` control request (the numbers behind `/usage`): without a prompt and only for signed-in accounts: in the background at most every ten minutes, and sooner when it matters — when you open the usage overview (every two minutes while it stays open) and after a Claude turn in Nook, at most once a minute per account; the refresh button in those views reads them at once (at most every ten seconds) (all slower when the energy plan takes it easy). The CLI uses its own login; Nook never reads, stores or forwards it. They are kept between launches.
- **Open What the Agent Points At:** a file link in an agent's answer (`src/app.swift:12:3`, `./README.md`, `#L20` anchors, `file://` links) opens in your editor at that line, read from the session's folder; in Nook's terminal, ⌘-click opens a local address in Nook's browser, any other web address in your browser and a path in your editor. Each editor gets the position its own way (`--goto` for VS Code, Cursor, Windsurf and VSCodium, `path:line:col` for Zed and Sublime Text, `xed --line` for Xcode, `--line`/`--column` for JetBrains), and a file is never opened in its default app. Changed files have a right-click menu: open in editor, show in Finder, copy the path or the path in the repository.
- **What a Session Costs:** a working session's header shows the CPU and memory of its agent and every process it started ("34 % · 512 MB"), read every three seconds while the session is on screen (`ResourceUsage`).
- **Worktrees That Clean Up After Themselves:** **Settings › Workspace** can remove a session's worktree once its pull request is merged, or 3, 7 or 30 days after the session settled (marked finished or archived) and went quiet. Both are on by default (after a merged pull request, and 7 days after the session settled), because a worktree holds its own build, often several GB; the **Worktrees** list shows how much disk each one takes. Antigravity's private TMPDIR, which macOS never empties, is cleared of anything older than two days when a session starts (`DiskUsage`). Every six hours Nook also removes build leftovers a worktree removal cannot reach: Xcode build folders and core-tests packages in temporary folders, Claude Code scratchpads, and the `.scratch/` of any worktree Nook knows (its own, its sessions', and `.claude/worktrees` in the repositories it works in) that went untouched for two days, and Xcode DerivedData of worktrees that no longer exist (`BuildLeftovers`, Settings › Workspace, logged as `build_cleanup`). A worktree in use, shared with another session, the main checkout, on another machine, or with changes that were never committed always stays; the branch is kept, so nothing committed is lost, and every removal goes to the action log (`worktree_cleanup`). Checkpoints, restores and removals of the same folder run one at a time (`WorktreeCleanup`, `FolderLease`).
- **Tidy Endings:** quitting Nook while sessions it runs are working asks first (not on logout, shutdown or an update restart; switch it off in **Settings › Workspace**), and deleting a session offers **Delete with worktree** when no other session uses its worktree (Git refuses one with uncommitted changes, so nothing is lost).
- **Setting Up Coding Agents:** the first-run flow has a **Coding agents** step (also opened from the empty Agents list with **Set up coding agents**): Claude Code, Codex, Gemini CLI, OpenCode and Cursor each show whether they are installed and signed in, with **Install** or **Sign in** running the same connect flow as Settings › Agents in a visible Terminal window; ACP agents you added are listed, and more can be added in Settings › Agents. Below, the git folders your agents worked in during the last 30 days can be added as projects with one click (`AgentReadiness`).
- **One Prompt, Several Models:** in a new session's model menu, **Send to several models** lets you click up to four models (of any connected agent) next to the chosen one. Sending starts one session per model, each in a worktree and branch of its own, titled with its model; the Agents list shows them under the first one, which carries a stack mark. When a model fails to start, the prompt stays in the box (and survives a relaunch) with only the failed models still chosen, and the box says which ones failed and why (`ModelComparison`, `WorkspaceManager.startComparison`).
- **Sessions per Project:** the Agents list puts the sessions that work or wait in a dropdown per project, as in Claude's own sidebar: every session in the same folder sits under that folder's name, and a session in an agent's worktree (`.claude/worktrees/…`, Nook's, Codex's, Cursor's) under the repository it was made from (`WorktreeOrigin`). A project with something waiting for you comes first, then the one with the newest activity; a folded project still shows the session open on the right and a dot when something in it waits for you, and the folded projects are kept across launches. Pinned, snoozed and settled sessions keep their own shelves. **Settings › Workspace › Group sessions by project** (on by default) switches back to the plain list (`InboxLayout.projectGroups`). This is the same list for every coding agent.
- **Where a Session Came From:** a session made with `/fork` (or **Fork**) keeps the session it came from (`WorkspaceRun.forkedFrom`, stored as its `lineage`). Its row in the Agents list carries a branch mark and sits under the original, and its header says **Forked from …** as a link that opens the original (a later model of a comparison says **Same prompt as …**). Sessions stored before this load unchanged.
- **Syntax Colors in Diffs:** every diff (a session's changes, a pull request's files) colors Swift, TypeScript/JavaScript, Python, Rust, Go, JSON, YAML, shell, CSS, HTML and Markdown. The diff shows plain at once; the colors are worked out in a background task (`SyntaxTokenizer`, `DiffSyntax`) and kept per file and content, so going back to a diff shows them right away.
- **Defaults per Project:** **Settings › Workspace › New session › Applies to** switches between the defaults for all projects and one of your recent project folders. A folder can set its own agent, model, access level, worktree on or off and branch prefix; every other value is marked **Inherited** and follows the global one, and the reset button next to an own value goes back to it. A new session in that folder (or a subfolder or worktree of it) starts with the result, and choices you make in the composer for a value the project sets stay out of the global defaults (`ProjectSettings`, built on `SettingsResolver`).
- **Stopping Stops Everything It Started:** every agent Nook runs gets a process group of its own (started with `posix_spawn` and `POSIX_SPAWN_SETPGROUP`), so **Stop** signals the agent together with the builds, shells and dev servers it started (SIGINT, then SIGTERM after the grace period, then SIGKILL). Live groups are written to `workspace/process-groups.json`; after a crash the next launch stops the groups an earlier Nook left behind, but only when the group leader is provably the same process (same pid, group and start time), never by name (`ProcessGroups.swift`).
- **Timelines That Survive a Crash:** a session's timeline is an append-only log in `~/Library/Application Support/Nook/workspace/runs.sqlite` (WAL, `0600`): each new event is written as it arrives, and a streamed answer or finished tool is written as a new version of that event, never by rewriting what is already there. Timelines are no longer cut off at 4,000 events (the panel still shows only the latest turns until you load earlier ones). The JSON timelines of earlier versions (`workspace/events/*.json`) are imported once and kept as a backup (`RunStore.swift`, `RunEventLog.swift`).
- **Replayable Agent Traffic:** `AgentProcess` talks to its agent through a `ProviderTransport`, so tests replay recorded transcripts (`apps/macos/Tests/Fixtures/ProviderReplay`, NDJSON: `emit_inbound`, `expect_outbound`, `expect_signal`, `exit`) through the real line handling and stream parsers (`ProviderReplayTests`). **Settings › Workspace › Keep agent traffic** (off by default) writes the same format per session process to `workspace/provider-traffic` (`0600`, at most 4 MB per process): it holds your prompts and the agent's answers, never the environment, and a log can be copied into the fixtures to reproduce a bug (`ProviderTransport.swift`).
- **Commit Messages in Your Style:** **Settings › Workspace › Commit messages** picks how Commit and Pull Request write their text: Nook's own style, Conventional Commits, like the repository (its recent commit subjects as examples), or your own instructions (`CommitStyle`).
- **Pull Request Review:** tick files as viewed (a mark lapses when a push changes the file), and open the **Guide** tab for a review guide: Claude Code or Codex reads the whole diff and writes the stops in reading order, each file with a note, what to look at closely and what to skim, and the questions only a maintainer can answer. The guide stays on this Mac and says when it was written for an earlier commit.
- **Quote Part of an Answer:** select words in an agent's answer and right-click › **Quote in your message** to put just that passage above your next message. With several questions from an agent, **Back** returns to an earlier one with its answer still picked.
- **Usage of Every Agent:** **Agents › Usage** (tabs **Cost**, **Tokens** and **Limits**) and **Settings › Coding agents** read the transcripts of Claude Code, Codex, Gemini CLI and Antigravity on this Mac (also sessions you ran in a terminal, for the last 90 days) and shows: cost at API list prices or tokens, over 24 hours, 7, 30 or 90 days; a large total with each agent's share; a stacked chart per agent (point at a column for its figures); totals for processed, cached and uncached input, output and cache savings; bars that split tokens and cost by type; and a breakdown per model (rank, share, a bar per model) or per day. A model opens with its cost per million tokens, cache hit rate and its own trend, and a model without a known price can get one (`UsageLedger`, `ModelRates`, `UsagePrices`). An agent with several accounts also shows them as one pool per limit window, a segment per account, with what the next reset gives back (`LimitPool`).
- **Full Transcript & Reasoning:** Reads agent transcripts to show collapsible reasoning steps (`thinking` / `thoughts`), commands, file edits, searches, and subagents inline. The conversation reads like a thread (`TranscriptPresentation`): your messages in a bubble on the right, answers as plain text on the left, steps in a row as one line ("Ran 3 commands and read 2 files"), each finished turn folded into "Worked for 1m 3s", and a running turn showing "Working for 12s" with the live step at its end and the thought that led to it right above. A message you sent while the agent worked splits the fold of its turn: the work after it folds into "Continued for 20s" under it. A turn you stopped stays open and ends in "You stopped after 12s". A context compaction ("Context compacted from 167k tokens"), an API error or a usage limit stays in sight when its turn folds. A command or another tool opens to its whole command line and what it gave back. A turn that changed files ends in a changed-files card ("3 changed files +12 −4", the files as a folder tree); a file in it, **Open diff** or `⌘D` opens the diff panel beside the conversation, where you pick the latest turn, any turn or all turns, and every file or one (`TurnDiff`, made from the agent's own edits). Sessions Nook runs get the same card and panel, with the lines and diffs read from git between the snapshots around each turn. A message you sent while the agent worked, from Nook, the terminal or the Claude desktop app, shows as your prompt marked "Sent while working" (Claude Code writes it as a queued command); away from the end, a pill brings you back.

## Nook Workspace MCP for Your Agents

Agents can use Nook's integrated terminal, browser, and PR workflow via a local MCP server (`~/.nook/nook-mcp`): start a dev server in a visible Nook terminal (`terminal_run`, `terminal_read`), open, inspect and drive pages in Nook's browser (`browser_open`, `browser_read`, `browser_screenshot`, `browser_snapshot`, `browser_click`, `browser_type`, `browser_wait_for`), propose and watch a pull request (`pull_request_create`, `watch_pull_request`, `get_pull_request_status`), propose scheduled tasks (`schedule_task`, `list_scheduled_tasks`, `update_scheduled_task`, `run_scheduled_task_now`, always after your approval), and ask you for a named secret (`request_secret`). Sessions started by Nook receive this automatically; external agents can be linked in **Settings › Workspace**. See [WORKSPACE-AGENTS.md](WORKSPACE-AGENTS.md).

## Connecting a Custom Agent

### 1. Via the Hook Script (Recommended)

The hook script is installed at:

```text
~/Library/Application Support/Nook/nook-hook.sh
```

Configure your agent to invoke it on each lifecycle event, passing the event JSON on `stdin`:

```json
{
  "hooks": {
    "UserPromptSubmit": [
      { "type": "command", "command": "\"$HOME/Library/Application Support/Nook/nook-hook.sh\" --agent my-tool" }
    ]
  }
}
```

- `--agent <name>`: Identifier under which the agent appears in Nook (lowercase letters, digits, `-`, and `_`, up to 32 characters).
- `<EventName>` (optional): Event name for agents that do not include `hook_event_name` in their JSON payload, e.g. `--agent my-tool Stop`.

### 2. Via the `nook_agent` JSON Field

If you cannot pass CLI arguments, include `nook_agent` directly in the JSON payload:

```json
{ "hook_event_name": "UserPromptSubmit", "session_id": "s1", "nook_agent": "my-tool", "prompt": "Write unit tests" }
```

### 3. Directly Over the Unix Socket

Send a single newline-terminated JSON line to:

```text
~/Library/Application Support/Nook/hub.sock
```

```json
{"agent":"my-tool","mode":"event","event":{"hook_event_name":"Stop","session_id":"s1","cwd":"/Users/you/project"}}
```

## Supported Hook Events

Nook normalizes event names from Claude Code and common aliases (`BeforeTool`, `preToolUse`, `beforeSubmitPrompt`, `PreInvocation`, `session_start`, etc.):

| Event | Nook Behavior |
|---|---|
| `SessionStart` | Marks the agent session as working |
| `UserPromptSubmit` | Starts a new turn; displays `prompt` as the current step |
| `PreToolUse` | Adds a running tool step (`tool_name`, `tool_input`) |
| `PostToolUse` / `PostToolUseFailure` | Completes the latest step as done or failed |
| `Notification` | Marks the agent as waiting for user attention; displays `message` in the notch |
| `Stop` | Marks the turn as finished; uses `last_assistant_message` as summary |
| `StopFailure` | Marks the turn as failed (`error`) |
| `SubagentStart` / `SubagentStop` | Tracks subagent lifecycle |
| `SessionEnd` | Removes the session from active lists |

## Quick Test

With Nook running:

```sh
echo '{"hook_event_name":"UserPromptSubmit","session_id":"t1","prompt":"hello","nook_agent":"demo"}' \
  | ~/Library/Application\ Support/Nook/nook-hook.sh
```

You will immediately see **Demo** in the notch with the prompt `"hello"`.
