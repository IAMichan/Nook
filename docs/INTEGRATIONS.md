# Integration Parity

Nook connects to many things of the same kind: chat apps, coding agents, connectors, AI providers, WhatsApp gateways,
and the apps on each platform (macOS, the iPhone companion, Linux, Windows, Android). The user sees them as one product.
When something works for one of them, they expect it to work for all of them, in the same way and in the same place.

## The rule

**A change to one integration is a change to its whole family.** When you add or change a feature for one integration,
do the same for every other integration of that kind in the same change, or write down why it cannot be done.

1. **Find the family.** Look up the kind of integration in the table below and list all of its members.
2. **Build it once, in the shared shape.** Put the feature in the family's shared type or view, not in one member. Each
   member then only translates what its app says into that shape. Never fork the UI per app.
3. **Fill it in for every member.** Wire each member that can support the feature. Check each one's API, protocol, or
   local data. Do not assume a member cannot support a feature until you have checked.
4. **Say what is not possible.** If a member's app does not offer the information (for example, Slack has no read
   receipts), leave it out on purpose. Note it in the matrix below and in a comment at that member. Never show a guess
   as if it were the app's own word.
5. **Test the shared logic once, and each member's parsing.** Every member gets a test for how it reads its app's data
   into the shared shape.
6. **Update this file** when a family or a feature changes, so the next change starts from a true picture.

If the user asks for something "in WhatsApp", it still applies to every chat app. If they ask for something for Claude
Code, it still applies to every coding agent. Mention any member you could not do in your summary to the user.

`AgentParityTests` holds coding agents to this. A check for one agent by name (`provider == .claude`) fails the test
when a file gets more of them than it has today. Give the feature a field in `ProviderCapabilities` or an exhaustive
`switch` over `RunProvider`/`AgentKind` instead, so every agent has to answer for it. Only when another agent's app
cannot offer it, raise that file's number in the test and write the gap in the feature matrix below. Every agent also
needs a column in that matrix.

## Side panel to composer

Everything the side panel hands to a session (Explain, Ask, Fix, Resolve on a pull request, an element pointed at in the
browser, a remark on a file's line) goes through `ComposerInbox` into the draft, as text from `SessionPrompts`. Both
composers take it (`AgentRunPanel`, `AgentSessionDetail`), so every coding agent gets it alike and none is left out.

## A session's pull requests in the side panel

The list at the top of the side panel's Pull request tab (`LinkedPullRequests`, `PullRequestSync.linked`) holds every forge
`SourceForge` reads, for every coding agent: it is built from a session's branch and has no agent-specific part. What a
member cannot do:

- GitHub has its own path; every other forge is a `PullRequestForgeClient` (`PullRequestForge*.swift`) with `PullRequestForgeFeatures`, so the page shows only what the forge offers. GitLab and the others are added under **Settings › Code › Pull requests › Code hosts** (`ForgeCredentials`; `email:token` (an Atlassian API token) for Bitbucket, `user:token` for Azure DevOps).
- GitLab: no emoji (a request per note). Request changes uses GitLab's own verdict (GraphQL `mergeRequestRequestChanges`, GitLab 18.9+, after adding you as reviewer); an older GitLab gets a plain note instead. A multi-line comment sends `position.line_range` with GitLab's line codes (SHA-1 of the path and both line counters from the patch). A revert does what GitLab's Revert button does (as): a `revert-<sha>` branch off the target, `commits/:sha/revert` onto it, and a merge request of it (the branch is deleted again when a step fails); a fast-forward merge of several commits cannot be reverted. A review with line comments is not atomic.
- Gitea, Forgejo: no emoji, auto-merge or revert (their API has no revert or cherry-pick); a thread cannot be resolved through the API, only read as resolved. A reply is a one-comment review. Draft uses the `WIP:` title prefix. A multi-line comment anchors on its last line: a review comment takes one `new_position`/`old_position`.
- Bitbucket Cloud only (bitbucket.org): no labels, emoji, auto-merge, branch update, revert (no API for it) or draft actions; reopen does not exist. A multi-line comment names its first line (`inline.start_to`/`start_from`).
- Azure DevOps (dev.azure.com only): no patch API, so Code lists names without diffs or line counts; no commit view, labels picker, reviewer requests, emoji or branch update; checks come from `/statuses`, not branch policies; editing your own comment is off because the viewer is not resolved. A revert is Azure's own operation (`/reverts` with the pull request as source, asked after until it finished) and then a pull request of its branch. Tags have no description.
- GitCafe: no line comments (its draft flow), emoji, auto-merge, branch update, revert, commit view or branch deletion; editing your own comment is off because the viewer is not resolved.
- Label descriptions show when the pointer rests on a label chip (`LabelChip`, `labelDescriptions` on rows and pages) for GitHub (GraphQL and REST), GitLab (the project's `/labels`), Gitea and Forgejo; GitCafe's are read when its API sends `description`. Bitbucket has no labels, and Azure DevOps tags have no description.
- Watched pull requests react to host events on github.com only (as): GitHub's event subscriptions (`POST /event-subscriptions` with the pull request's URL and its review, head, state and merge conflict events) and the server-sent event stream they return (`GitHubPullRequestEvents`, `PullRequestEventFollower`, `GitHubPullRequestEventStream`). Each event and each (re)connect reads that one watch at once (`WorkspaceManager.checkPullRequestWatches(url:)`); the two-minute sweep stays as the fallback. A 403 pauses the feed for an hour, the subscription limit (422) for ten minutes, a pull request no account sees (404) for an hour; 45 s of silence is a dead stream; after six failed connections in a row the feed ends and is asked for again a sweep later; the subscription is deleted when the watch stops. Feeds stop while the energy plan pauses, and for a badge-only watch while nobody is at the Mac. Nook has no GitHub App sign-in, so the connected accounts' own tokens subscribe; a stream one account may not read moves to the next. GitHub Enterprise, GitLab, Gitea, Forgejo, Bitbucket, Azure DevOps and GitCafe have no event stream a client can follow (only webhooks to a public server) and are polled.
- GitHub's own stacks (`/repos/{repo}/stacks`) and their asynchronous merge are github.com only.
- A merge or close from the agent's shell (`gh pr merge`, `glab mr merge`/`accept`, `tea pr merge`/`m`, `fj pr close`,
  `cafe pr merge`, `az repos pr update --status completed`) reads the session's linked pull requests again at once
  (`PullRequestToolCall.closesPullRequest`, `PullRequestSync.recheck`), for every coding agent Nook runs. Bitbucket has no
  such CLI. A session Nook only sees (an agent in a terminal) waits for the next round.
- A pull request the agent works on with `gh pr …` or `glab mr …` (`checks 3877`, `checkout`, `view`, `-R owner/repo`) or
  that you name in your message ("#3877", a link) is linked to the session (`PullRequestMentions`,
  `WorkspaceManager.noticePullRequests`, `PullRequestSync.mention`), and the tray above its composer lists it next to the
  branch's own, with every pull request it watches. A "#12" from your message is linked only once the forge confirms it
  is a pull request; one you took off the list stays off. It reads the shared timeline, so it holds for every coding
  agent Nook runs; `tea`, `fj`, `cafe` and `az` commands are not read yet, and a session Nook only sees (an agent in a
  terminal) has no tray above a composer of Nook's.
- The other platform apps (`apps/tauri`, `apps/ios`, `apps/android`, `apps/windows`, `apps/linux`) have no session side
  panel with a pull request tab, so there is nothing there to change.

### One inbox for every app

Every chat Nook shows lives in one place, the shared inbox (`ChatInbox`), whichever app it is in: the Chats tab, the
cards in the notch, search, the iPhone companion and what Nook reads (`chat_inbox`) all read it, and one rule says which
chats show (`ChatCaptureService.isShown`: the app is on, you did not hide the chat, and WhatsApp comes from one place at
a time). Each app's bridge only translates what its app keeps into it. WhatsApp through the linked phone is one of them
(`WhatsAppGatewayBridge`): its link keeps WhatsApp's own state (the gateway, the JIDs, each person's emoji, each voter's
choice, each member's ticks) and `WhatsAppExport` turns it into the shared shape. Its messages are kept in memory only, as
they always were (`BridgedChat.ephemeral`: `chat-inbox.json` holds WhatsApp's chats without their messages); the files a
chat showed stay in Nook's caches like every other chat app's (`WhatsAppLink.fileKey`, at most `filesLimit`, removed when
WhatsApp is turned off), so they show at once after a restart. The
link tells which message is news (live, not history, not a catch-up after the Mac slept: `ChatNewsBridge`).

A chat its app knows by an id of its own (`BridgedChat.chatID`, WhatsApp's chat key across accounts) is kept by it, so a
new name never splits it and two chats with one name stay two. Ids from before (`wa|<key>`) are read as the new ones
(`ChatIDMigration`) wherever something was kept under them (hidden messages, drafts, the chat opened last).

### Mail

Mail is a chat app like the others. `MailBridge` reads the Mail app on this Mac, and with it every account Mail holds,
whatever kind: iCloud, Gmail, Outlook and Exchange, Yahoo, any IMAP or POP account. Each person you write with is one
chat per account (`MailChatData.chatID`, `<account>~<address>`): their mail from the account's inbox, yours from its
Sent mailbox, each message as its subject in bold over the start of its own text (the quoted earlier mail left out,
`MailChatData.text`). With more than one account each chat is named by its account, as WhatsApp's are. Newsletters and
notifications (`MailChatData.isAutomated`) are the app's channels and stay quiet by default (`ChatNoticeRules`).

Nook reads Mail only after you linked it, in Settings › Chat apps › Mail or from Mail's empty list in the Chats tab (the
first read asks for Automation), and only while Mail is open, as the Mail connector does: it never starts Mail in the
background on its own. Linking it, or "Read Mail now" while Mail is closed, starts Mail out of sight once, so the first
chats show at once. A read in which not one account answered says why instead of showing an empty list. An answer goes out through Mail
(`MailSender`) as a reply to the chat's newest mail from the chat's account; "Mark as read" sets Mail's read status,
which tells the server. A mail chat shows as mail, not as bubbles (`MailThreadView`): a card per mail with its headers, attachments and whole
text (read from Mail when it opens, `MailBridge.message`), the quoted mail folded away. Reply goes to the field under it;
Reply all and Forward, and New mail in a mail app's list, write in the pane beside the list (`MailComposeView`), from
any address of any account, sent through Mail after your click and logged as `send_mail`. Mail apps Nook cannot read itself (Outlook for Mac, Gmail and Outlook on the web, Spark, Proton
Mail) are members by their notifications: `ChatCapture.mailNotice` reads the subject from them the same way. Mail has no
emoji, edits, polls, typing or read receipts another app can reach. An opened mail's attachments are saved by Mail
(`MailChatData.messageScript(saveTo:)`) and shown in its thread view: photos inline, other files as a tile that opens them.

### One way for every action

Everything you do in a chat from Nook goes through `AppModel.runInChat` (`App/AppModel+ChatSend.swift`), whichever app
the chat is in: sending text or an item, an emoji, a vote, an edit, a deletion, "Mark as read in <app>", pinning, muting
and archiving. It first checks what holds for every app (`ChatAction.refusal` in `ChatContract.swift`): the chat's
`ChatAbilities` take the action (the same list the Chats tab draws its buttons from, so a button and its action never
disagree), there is text where text is sent, and a message changed or deleted for everyone is yours. Then the app's
bridge does only its own translation. Afterwards the chat is read again from its app at once (`readSoon`; the WhatsApp
gateways push their changes themselves), and the action is logged under one name per action (`chat_send`,
`chat_react`, `chat_vote`…) with the app in the entry. A new chat app adds a case to `ChatRoute`, its line in
`chatAbilities`, and its call in each action's `switch`; nothing else.

"Mark as read in <app>" reads the chat in Nook at once, and counts it as read in the app (and logs it so) only once the
app took it. When the app refuses, a toast says why; so does an app that has no message of the chat to mark (a Telegram
chat only its notifications brought, a Teams chat without a message Nook knows), instead of claiming it was read. What
the app is told is what you saw when you clicked: a message that came in while the call went stays new. A chat you
marked unread by hand (`InboxThread.markedUnread`) is marked unread in its app too where the app takes it
(`AppModel.markChatUnread`; a refusal says why in a toast and Nook's mark stays), and stays unread until you read it, whatever a lagging or windowed count
of its app says at its next read. A chat that an app names twice is read with its twin (`ChatInbox.twins`), so the badge
does not keep counting the one the tab hides. WhatsApp's linked phone keeps its chats in the tab through a short moment
its gateway does not answer (`WhatsAppLink.holdsChats`, ten minutes at most).

An open chat is the same for every app too (`App/AppModel+ChatOpen.swift`): opening it reads it from its app, the
pointer resting on it fetches what the click needs, scrolling back asks its app for older messages, a file opens from this
Mac or its app, and the chat is online where its app needs that to say who types (WhatsApp). The Chats tab never asks
where a chat came from.

Which chats reach you is the same for every app (`ChatNoticeRules`, kept by `ChatNoticeRulesStore`, chosen in each app's
sheet in Settings › Chat apps with `ChatAppNoticeRows`, and on a chat's card with Quiet and Hide): a kind of chat can stay
quiet (groups, unless a message mentions you; WhatsApp's status updates and channels too), each chat can be automatic,
always or never, and a hidden chat never shows, counts or reaches you until you show it again. The first launch took over
what Settings › WhatsApp kept, for every linked account. WhatsApp's link sorts its gateway's messages by the same rules.

In Settings › Chat apps every linked account is a `ChatLinkedAccountRow`: one rule (`ChatAccountHealth`) says whether it
reads, is off in Nook, fails for a passing reason, or is signed out (`ChatCaptureService.bridgeSignedOut`, per account
for Teams), and only the last offers "Sign in again". WhatsApp's accounts keep their own list (`WhatsAppAccountList`):
a linked phone's state is the gateway's, not a read's.

### One way for every read

Every bridge reads on its own turn, side by side (`ChatCaptureService.pollBridges`): a slow web service never holds up
a quick one. The chat helper reads a chat again when the chat list moved past the newest message it got
(`ChatServiceData.isBehind`, up to three times), so a chat's row never shows an older message than the chat itself.

Within one read, a bridge that asks its service per chat asks for the chats that moved side by side, six at a time
(`ChatParallel`), and goes through the answers in the chats' own order, so what it remembers per chat is written as
before. A read of fifteen chats then takes about as long as three. A chat's own failure leaves the others; a lost
sign-in or a rate limit (`ChatParallel.Asked.refused`) stops asking for the rest of the round. This holds for the chat
helper (Instagram, Signal, Messenger, X, LinkedIn…; the chats told to have changed, such as one you just opened, are
asked first), Teams (Graph and the website, each with its pictures and read receipts) and Slack (the same requests as
before, in a fraction of the time). Left out because their app does not ask per chat: Telegram (TDLib pushes each
chat's history by itself), WhatsApp through the linked phone (the gateway pushes), Messages and WhatsApp on this Mac
(one database query), Mail (one AppleScript per account; Mail answers scripts one at a time) and Snapchat (one hidden
web page reads one chat at a time).

A read that fails waits longer each time, the same for every bridge (`ChatBackoff`): a minute (or the bridge's own
interval when that is longer), then twice as long after each failure in a row, up to a quarter of an hour. A bridge that
reads a database on this Mac (`ChatBridge.readsLocally`: Messages, WhatsApp on this Mac) starts at five seconds after a
passing failure (the app held its lock), and at a minute without Full Disk Access. A notification or a send from Nook
does not cut that short; signing in again does. A database the app kept locked past the wait is read without its
write-ahead log, where the newest rows may still be (`AppDatabase.read`, `complete`): Messages, WhatsApp on this Mac and
the notifications then read again at their next turn, also when the database did not change since, so a message still
in the log never waits for the app's next write. A bridge counts as reading an app only
while it is ready (signed in, its app not taken over by the chat helper), so its last good read never hides the app's
notifications or keeps the helper from reading that app. Cursors move only once a whole read worked (Messages' rows and
tapbacks), and a later read follows every page newer than the last one it read (Slack, five pages of 30), so a busy
chat loses nothing between two reads. Uploads and long fetches (a file sent, the helper scrolling back) run on
`ConnectorHTTP.transferSession`, so they are not cut off after 20 seconds.

Every app also gets what is certain from later messages (`ChatReceipts.filled` and `filledReaders`). Someone who read
a later message of yours read the earlier ones too. In a private chat, their message after yours means yours reached
them. Neither WhatsApp gateway keeps receipts. So a message whose receipts came while Nook was not running (or before
it was linked) shows only what those rules prove.

WhatsApp can link more than one account through the same gateway (Settings › Chat apps › WhatsApp › Add account): each
account is a `WhatsAppLink` of its own, on its own GOWA device or OpenWA session (named after its `WAAccount` id), with
its own QR, webhook port (the first account's port plus its place in the list) and read marks. The rest of Nook knows a
chat by its key across accounts (`WAChatKey`): the first account's chats by their JID alone, so nothing kept from before
changes, another account's as `<account id>~<JID>`. `WhatsAppAccounts.route` finds the account and the JID again. The
choices per kind of chat and per chat hold in every account. WhatsApp on this Mac (its database) and the chat helper still
read one account each: the WhatsApp Business app for the Mac keeps its own database, which Nook does not read yet.

A linked phone's messages come in on the gateway's webhook the moment they arrive. Without a webhook for five minutes,
Nook asks the gateway every ten seconds; with one, it still asks once a minute (`WhatsAppLink.safetyPollGap`), since a
webhook that keeps bringing ticks and typing may still have dropped a message.

While a WhatsApp chat is open in Nook, Nook tells WhatsApp this device is online, as WhatsApp Web does. Otherwise
WhatsApp sends no typing updates. While it is online, the phone may hold back its own notifications.

## Coding agent timeline

translates its own output into `AgentSignal`s, and `AgentTimeline` writes them by the same rules for every agent (one
answer and one thought streaming at a time, a tool call is one row from start to end, nothing stays running after the
turn). Add a provider by translating into those signals, never by writing `RunEvent`s for text, thinking or tools
yourself.

Sessions in a terminal are read from the agent's own transcript (`AgentTranscript`). Claude Code and Codex give
messages, thinking, steps with their outcome and output, compactions and errors. Gemini CLI's chat file gives messages,
thoughts and its `toolCalls` as the same steps (with outcome, output and the lines an edit changed).

Both kinds of session draw their conversation with the same views, so a session reads the same whichever agent runs it
and whether Nook or a terminal runs it: messages are `TranscriptUserMessage` and `TranscriptReply`
(`TranscriptMessage.swift`), the work between them `TranscriptWorkLine`, `TranscriptThought`, `TranscriptStepDetail`,
`TranscriptWorkGroup`, `TranscriptFold`, `TranscriptWorkingLine` and `TranscriptLiveLine` (`TranscriptWork.swift`). A
session Nook runs translates a tool call into the transcript's step with `AgentToolStep(event:)`; a new kind of row is
added to those views, never drawn by one side alone. The iPhone companion draws its conversations with the same rows
(`TranscriptViews.swift`): the Mac sends a session Nook runs and one in a terminal as the same `TimelineEntry`s (a step's
summary without its tool's name, a compaction marked `TimelineEntry.compacted`), and the phone groups steps under the
Mac's sentence ("Ran 3 commands and read 2 files"). The phone gets no thinking and no tool output, for either kind of
session.

A session's title is the name the agent gave it, when it gives one: Claude Code's `custom-title` lines (the Claude app
names every session, `/rename` too), Codex's `thread_name` in `session_index.jsonl`, and Antigravity's
`conversation_summaries.db`. Gemini CLI's chat files hold no name, so its sessions take their first prompt. A session Nook
takes over without either is named after its first question and then gets a written title (`generateTitle`), never the
folder name.

Titles, commit messages, pull request text and the suggested next prompt are written by the generator chosen per task in
Settings › Sessions › Text generation (`TextGenerator`). The default is the agent's CLI: Claude Code
(`claude -p --model haiku`) or Codex (`codex exec`), the session's own when it is one of the two, otherwise whichever is
connected, so a Gemini, Cursor or ACP session gets its text from those. The other choice is a model API that only writes
text (`TextGeneratorAPI`: Anthropic's Messages API, or `/chat/completions` for OpenAI, OpenRouter, Ollama, LM Studio and
the brain's other API providers), with the key the brain settings keep in `SecretStore`. An API without its key falls
back to the agent; a failed API request gives no text (the caller's fallback, as for a CLI that gave none) rather than a
quiet run on your subscription. Review guides always use the agent: they read the whole diff. Flow's dictation clean-up
is not one of these tasks: it already runs on Nook's brain, which is itself a choice of model, and it must answer fast.

## Platforms and chats

The iPhone companion is the only other app with the Chats tab. It gets the same things as the Mac over the companion
protocol. The filled-in ticks come in each `InboxLine.ticks`. Who read it comes in `InboxLine.readers` and opens from

## Open gaps

- **1Password references** (`op://…`) are read for secrets agents ask for and for MCP server variables and headers. The
  built-in connectors' own credential fields and an agent account's variables (Settings › Agents) still take the value
  itself: they are read synchronously at launch, where waiting for `op` (and Touch ID) does not fit yet.
- **Publishing a project** goes to GitHub only (`GitHubRepositoryCreate`); GitLab, Gitea and the other forges Nook reads
  pull requests from do not create repositories yet. Agents cannot ask for it over the workspace bridge: you start it.
- **Nook in another app (remote MCP)** serves Claude.ai and ChatGPT alike through one HTTP endpoint with OAuth
  (`RemoteMCPServer`). It offers the tools that need no project folder (sessions, pull request status, chats, Nook's apps,
  scheduling); terminal, browser, simulators, pages, secrets and screen control stay with agents in Nook. Not verified against
  the live assistants: that needs a deployed relay and a Claude.ai or ChatGPT account (docs/WORKSPACE-AGENTS.md).
- **Teams files.** Pictures pasted in a Teams message show and can be sent (Teams' media service, with the website's
  session). Other files live in SharePoint or OneDrive, which Nook does not reach: they show as a file row that opens
  Teams, and Nook does not send them. Chats read only through Microsoft Graph do not fetch pictures yet.
- **Snapchat** is read from Snapchat for Web's page (`SnapchatWebData`), not from a service: Snapchat has none, and no
  bridgev2 connector for it exists. It shows the chat list and the messages of chats you load in Nook, and answers with
  text and pictures (handed to the website's own file button, paste or drop: a change to the page can stop that, and
  Nook then says the picture was not sent). Other files, emoji, edits, deletions, pinning, muting, archiving, read
  receipts and typing are not offered for it, and its messages carry the time Nook first saw them, since the website
  shows none. Pictures in a chat are saved while Nook has it open, so a picture only shows after that chat was read.
- **Mail** is read from the Mail app (`MailBridge`), every account in it, while Mail is open. An opened mail's
  attachments are saved by Mail and show in the mail view (a photo as itself); one Mail cannot save (larger than
  `ChatMedia.maxBytes`, not downloaded yet) stays a name to open in Mail, and the chat list does not show attachments.
  Scrolling back past the newest 60 inbox and 40 sent messages per account, and Outlook for Mac's or a web mailbox's own accounts (they
  come in by their notifications only; Nook answers them in a new mail through the Mail app) are not there yet.
- **Conditional reads and forge lanes.** Reads of every forge go through `ConditionalFetch` (an `ETag`, so an unchanged answer
  has no body) and one `PullRequestRound` lane per host; a forge that sends no `ETag` is simply read in full. An action's
  answer updating every row at once (`PullRequestActionReply`) exists for GitHub only: the other forges' `perform` returns
  no state, so their page is read again. `apps/tauri` has neither.
- **CI logs of GitLab merge requests.** A GitHub check's steps and log open in Nook (`CICheckLogView` on the Mac,
  `CheckLog.svelte` in `apps/tauri`). A watched GitLab merge request still opens its pipelines page in the browser:
  Nook does not read GitLab job traces yet.
- **The Actions page for GitLab.** A GitHub repository's workflow runs (CI, a promote, a release), their jobs and logs,
  re-run and cancel are on the Actions page (`ActionsPanel` on the Mac, `views/agents/actions` in `apps/tauri`); a run
  that has no jobs, and so no log, says why. A
  GitLab project's pipelines are not listed there yet: Nook reads no GitLab pipelines API.

- **Agent credits in merge commits.** With Settings › Agents › "Leave agent credits out when merging" on, a merge Nook
  makes on GitHub (the pull request page, quick merge, Nook Chat's merge tool) asks for GitHub's own merge or squash commit
  without agents' `Co-authored-by:` trailers and "Generated with …" lines (`AgentCredits`, `PullRequestMergeMessage`),
  keeping the people GitHub would credit. A rebase merge keeps every commit as it is, and a merge commit keeps the
  branch's commits, so their trailers stay in history. GitLab merge requests have no merge action in Nook yet.

- **Agent credits in an agent's own commits.** With Settings › Agents › "No agent credits in commits" on, every coding
  agent Nook starts is told to write no `Co-authored-by:` trailer and no "Generated with …" line for itself or any other
  AI (`AgentCredits.commitsNote`, through `AgentCredits.launchInstructions` for Claude Code, Codex in both its modes,
  Gemini CLI, and the ACP agents: Cursor, OpenCode, Grok, Antigravity and the ones you add). Claude Code also gets
  `includeCoAuthoredBy: false` and an empty `attribution` in its `--settings`, so it never adds them by itself; the
  others have no such switch, so they rely on the instruction. A pull request an agent opens through Nook's
  `pull_request_create` has the credits stripped from its description. Agents running in your own terminal, remote
  sessions, and `apps/tauri` are not launched by this Mac's Nook, so the setting does not reach them.

- **The GitHub dashboard in Chats (Tauri).** Pull requests and reviews sorted by what needs you, issues assigned to you,
  approving, commenting and asking for changes, and the merge rights check exist for GitHub only. GitLab merge requests
  are still only watched and opened in the browser; Nook has no GitLab review or merge actions yet.

- **Mentions outside WhatsApp.** "Groups quiet unless they mention you" knows a mention only where the app says it:
  WhatsApp's gateways do (`mentionsMe`). Telegram (`contains_unread_mention`), Slack (`<@you>` in the text) and Teams
  (a message's mentions) say it too, but their bridges do not read it yet, so a quiet group of theirs stays quiet.

- **Searching the whole chat history from Search everything** (`ChatSearchBridge`) reaches Messages, WhatsApp (this
  Mac's database and what the linked phone brought), Telegram and Slack. The chat helper's networks, Teams, Snapchat and
  Mail are searched in the newest messages Nook keeps of each chat (`ChatInbox.keep`) only: the helper has no search call
  yet, Teams' search needs a Graph scope Nook does not ask for, Snapchat's website has none, and Mail's search goes
  through AppleScript, too slow for every keystroke.

- **Music players: queue and Up next.** "Add to queue" in the Music tab goes to the playing player's own queue: Spotify
  through its Web API (`SpotifyWebAPI`, after connecting Spotify in Settings › Services with the user's own client ID;
  Spotify allows this only with Premium), Music through its own Song › Add to Queue menu item (`MusicAppQueue`, needs
  the Accessibility permission and the track in Music's library or current playlist). When the player cannot take it,
  Nook keeps the track in its own queue and starts it itself. Up next reads Spotify's real queue once connected; for
  Music it still shows the playlist order, because Music's own queue cannot be read by another app.
- **Music players: search.** The Music tab's Search section finds tracks in the playing player: Music's library through
  AppleScript (`search library playlist 1`, so only tracks in the library, not the Apple Music catalogue), Spotify
  through its Web API search (needs Spotify connected in Settings › Services, not Premium). A found track plays on
  click and goes in the queue like any other track in the tab.
- **Music players: starting a track.** Everything the Music tab and the brain start goes through
  `NowPlayingService.playInBackground`: Spotify through its Web API (`PUT /me/player/play`, Premium and an awake device),
  with the AppleScript `play track` as the fallback; Music through AppleScript. A player that does not run is started
  hidden, and one that takes the front anyway is put back (`MusicPlayerFocus`). Spotify's own "open" button in the bar
  still opens it. A track plays in the player it came from, and the other player pauses.
- **Music players: listening history and statistics.** Nook measures what it hears from both players in the same way
  (`MusicListening`, `MusicHistory`, `MusicStats`, in `music-history.json` on this Mac; Settings › Connections turns it
  off or clears it). Only Spotify adds plays from elsewhere (`/me/player/recently-played`, last 50). The player's own top
  lists differ: Spotify's top of the last six months (`/me/top`, no counts), Music's all-time `played count`, read only
  while Music runs. Music has no per-play dates, so it cannot fill in plays Nook did not see. Spotify's history and top
  lists need two newer scopes; a connection made before them asks to connect again, the rest keeps working.
- **Music players: playlists.** The Music tab's Playlists section shows and keeps the user's playlists in both players:
  Music through AppleScript (`MusicScriptOutput`: list, tracks, add with `duplicate`, remove, make, rename, delete;
  smart playlists are read only), Spotify through its Web API (`SpotifyWebAPI`: `/me/playlists`, a playlist's
  `/items` with a fallback to the older `/tracks`; playlists of others are read only). A playlist opens as a track
  list to play, shuffle, filter and edit; "Add to playlist" sits in the bar, the full player and every track's context
  menu. Spotify needs the playlist scopes, so a connection made before them asks to connect again
  (`Failure.missingScope`). With nothing playing, the tab offers the playlists to start from.
